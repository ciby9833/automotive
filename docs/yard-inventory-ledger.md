## 业务规则

| 操作 | 入口与结果 | 库存数量 | 本次入场时间 |
| --- | --- | --- | --- |
| 手工/扫码入库 | 共用 InboundService；校验有效订单、机构、场地、车辆、照片和可用库位，同时更新车辆、库位、库存及流水 | +1 | 实际入库时间 |
| 普通/批量移位 | 仅移动本场地已有库存；不能通过批量移位新建库存或跨场调拨 | 不变 | 保留 |
| 撤销误入库 | 原“释放库位”入口已移除；原因必填，保留变更前后资料及照片引用，撤回到预计到仓 | -1，单列撤销 | 原记录保留，结束本次库存记录 |
| 装车 | 有装车照片，释放停车/待装库位，变为“已装待出场” | 不变 | 保留 |
| 卸车回库 | 网页选择实际停放库位；接口未指定时仅在原库位仍可分配时回原位，否则拒绝 | 不变 | 保留 |
| 整单启运 | 全部 VIN 已装车、司机及运输车辆齐全，整单事务登记实际离场 | 每辆 -1，计入今日出库 | 本次库存记录关闭 |
| 签收 | 只允许已启运的运输中派送运单；签收不再次扣减库存 | 不变 | 不变 |
| 盘点调增 | 独立权限；盘点单号、原因、实际到场时间、照片、库位必填；已有有效入库订单，且未关联出库业务 | +1，单列调整 | 使用填写的实际到场时间 |
| 盘点调减 | 独立权限；盘点单号、原因必填；不得替代正常发运 | -1，单列调整 | 原记录保留，结束本次库存记录 |

已经关联出库计划、开单或装车的车辆，禁止直接撤销误入库或盘点调减；先处理关联出库业务。撤销运单前必须先卸车回库。

批量移位逐行提交并返回成功、跳过和失败明细；不能把部分成功当作整批成功。失败行不改变库存、库位或库龄。

## 库存与数量核对

`yard_inventory` 表记录每次在场周期及当前位置；同一 VIN 只能有一条未关闭记录，一个库位只能关联一条在场记录。`entered_at` 是本次到场时间，移位、装车和卸车都不重置。

`inventory_movements` 是独立业务流水，不再从操作日志估算入库、发运数量。每条流水有业务类型、数量变化、操作人、时间、原因/盘点单号、运单关联和变更前后快照；数据库禁止更新或删除，纠错通过新的业务动作表达。

按机构配置的时区和业务日切计算：

> 期初库存 + 当日初始化基线 + 正常入库 − 实际发运 − 撤销误入库 + 盘点净调整 = 账面期末库存

看板同时显示当前在场库存及账面差异。数量核对在同一条查询中读取流水和当前库存，避免并发提交导致两次查询读到不同版本而误报差异。装车、卸车、移位的数量变化为 0。盘点和撤销不混入“今日出库”。

库存列表、场地格子、总览及滞留预警均读取机构 `long_stay_days`。库龄取本次到场时间，已装待出场车辆也计入库存及长龄预警。

每日库存快照改为从库存流水还原截止时点位置，包含没有停车库位的已装车辆；每日数量变化快照直接读取流水。已完成历史快照保持不可变。

## 容量和位置

- 设计容量：区域规划的排数 × 位数之和。
- 启用容量：启用场地、启用区域内已经生成的库位数，包含冻结位。
- 可分配空位：启用容量内，空置且未冻结的库位。
- 冻结容量：启用区域内锁定的库位数，可能有车，也可能空置。
- 停用容量：停用区域内已经生成的库位；整个场地停用时其全部已生成库位均计入停用容量。
- 未生成容量：设计容量减已经生成的库位数。
- 可用容量：启用容量减冻结容量；利用率为其中已占用库位 / 可用容量。

区域用途为停车区 PARKING 或待装区 STAGING；有车时禁止变更用途。车辆另有 LOADED 已装待出场位置，不能用“无库位”直接判定离场。

在场车辆 = 停车区车辆 + 待装区车辆 + 已装待出场车辆。车辆数量与停车位数量分别展示。纯运输创建/调度的场地库存排除检查也改为读取在场库存，已装车车辆不能借空出的库位绕过检查。

## 审计保障范围

入库（含计划外散车）、移位、撤销误入库、盘点调整、装卸车、启运、签收、区域维护，以及出库开单、撤销运单、司机/拖车分派，业务变更与对应审计使用同一数据库事务。任何必要审计写入失败，业务一起回滚。实时推送和通知在事务提交后发送，通知失败不把已提交业务误报为失败。

撤销运单先在同一事务内写快照再删除运单。原实现删除后写带外键的日志可能失败并被忽略；现在保留原运单 ID、编号和撤销前快照，即使关联外键被置空也能追溯。

本次还补齐了代码已有而数据库迁移缺失的区域维护审计枚举。库存审计使用显式事务参数；客户、承运商等不属于本次修复的旧模块仍沿用原日志写法，不能据此宣称全系统所有操作都已改为强事务审计。

## 数据迁移与上线

迁移：`backend/src/database/migrations/1790300000000-InventoryLedger.ts`。

1. 发布前备份数据库；协调停止库存业务写入，执行迁移，再启动新后端及网页版本，避免旧应用继续只修改库位。
2. 迁移先校验占用库位与车辆记录、到仓状态、真实到仓时间、机构归属及重复占位。发现不一致时整次迁移中止，先按实际凭证核对数据；不会猜测 VIN 归属或补造入库时间。
3. 以真实到仓时间建立现有库存，并纠正过去批量移位重置的库位时间。已有装车未启运车辆转为 LOADED，释放原停车库位。
4. 迁移只建立 OPENING 基线，不伪造迁移前的入库/发运流水。迁移当天看板单列初始化数量。
5. 新口径快照从迁移后的完整业务日开始；历史已完成快照保留。历史缺少可用容量时利用率比较返回无基线，不套用旧分母。
6. 为需要执行盘点的既有角色分配新增的 `yard:adjust-inventory` 权限；不会自动扩大已有角色权限。手工入库及盘点调增需文件上传权限。
7. 上线后核对库存公式差异为 0，并抽查停车、待装、已装待出场车辆。数据库记录不能代替现场实物盘点。

迁移不支持自动向下还原；若需要回退，应使用迁移前备份和配套旧应用版本，不能直接删除库存流水表继续营业。本次未在业务数据库执行迁移，也未发布上线。
