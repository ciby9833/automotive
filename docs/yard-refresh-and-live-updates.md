# 场地接口重复刷新排查与修复

## 已确认的原因

排查对象为生产 `/api/yards/:yardId/slots` 和 `/api/yards/:yardId/stats`，以及调用它们的场地看板。生产地址的匿名只读请求返回 401；未取得生产登录态或服务器监控，因此本文不推断当前生产 QPS、响应耗时或最大承载量。

源码中的行为已确认：

1. `YardBoardInner.tsx` 原来每 30 秒同时请求全量 slots 和 stats，数据没变化也执行。除移位模式外，没有检查页面是否可见、上一轮请求是否结束。
2. `AppShell.tsx` 为保留工作台状态，用 `is-hidden` 隐藏其他标签页，而不是卸载。因此切到其他业务页后，场地看板仍然请求；总览也有独立的 60 秒定时器。
3. 原 stats 会取出全部库位、区域和在场车辆，再在 Node.js 中遍历计数。它与 slots 重复读取库位。每轮两次接口合计 7 次业务查询，另有认证与权限查询。
4. 已有 TrackingGateway 不等于场地实时更新已经生效：页面没有订阅它，且发布主要由运单状态变化触发，没有完整覆盖场地操作。
5. 慢请求会与下一轮重叠；切换场地后，较晚返回的旧场地响应也缺少独立取消保护。

单个保持挂载的场地看板约产生 `2 × 3600 / 30 = 240` 次请求/小时。假设同时有 1000 个这种页面，仅两个接口约为 66.7 请求/秒；这是按代码算出的示例，不是生产观测结果。请求数、全量返回体、应用层对象分配以及重复数据库查询都需要控制。

## 新的更新方式

```mermaid
flowchart LR
  A[入库、移位、装卸车、启运、区域或策略变化] --> B[数据库事务提交]
  B --> C[数据库发送变更通知]
  C --> D[各后端进程的常驻监听]
  D --> E[通知有权限且正在查看相关页面的连接]
  E --> F[前端合并连续通知，单次读取]
  F --> G[首次全量；后续库位增量和最新统计]
```

- 工作台当前标签及浏览器文档都可见时才建立订阅。隐藏时断开连接、取消在途请求、停止校准定时器，保留页面已有数据。
- 恢复页面、网络恢复、WebSocket 重连时补查。首次先订阅再查询；连接未及时建立时 750 毫秒后仍可通过 HTTP 加载。
- 一次只进行一个刷新请求；连续通知合并，读取起点至少间隔 2 秒。请求进行中若又有变化，完成后再补一次，避免漏掉末次变化。
- 约每 4.5～5.5 分钟做一次带随机错峰的校准，覆盖通知丢失、WebSocket 被代理阻断，以及长龄、预警和业务日切等随时间变化的指标。
- 空闲且一直可见的看板约为每小时 12 次校准请求，另计首次加载、实际业务变化、人工操作和重连。WebSocket 保活为轻量帧，不会调用 slots/stats 查询。

通知基于 PostgreSQL `LISTEN/NOTIFY`，只在事务成功提交后送达；相同事务里的重复通知由数据库折叠，服务端再合并短时间的变更。每个后端进程各自监听同一数据库，避免多进程部署漏通知。数据库连接丢失后自动重连并要求页面补查。[PostgreSQL 官方说明](https://www.postgresql.org/docs/current/sql-notify.html)

连接按场地或已授权机构订阅，不逐次遍历所有用户并查权限。WebSocket 只发送“有变化”的信号，不推送 VIN、数量或业务明细；实际数据请求继续经过现行 HTTP 权限和机构范围校验。JWT 到期后连接关闭。[Socket.IO 房间机制](https://socket.io/docs/v4/rooms/)

## 查询与传输优化

新增 `GET /yards/:id/board?since=<version>`，供场地看板使用：

- 首次返回全部库位、统计及版本标识。
- 后续返回变化的库位、删除的库位 ID 和最新统计；没变化时不重传库位数组。
- 客户端可以跳过中间多个版本，服务端合并这些版本的变化。
- 后端重启、切换到没有对应缓存的进程、客户端版本过旧时，自动返回全量，避免用不完整增量拼库存。
- 版本和增量只是可丢弃的读取缓存，不增加第二套库存事实或业务写入逻辑。

场地 stats 改为数据库聚合，应用不再读取全部在场车辆用于计数。场地 board 每次缓存未命中时，场地启停状态、库位和统计都在同一个可重复读事务中获取，避免来自不同数据库快照。运营总览仍有明细查询和应用层聚合，尚未整体改为 SQL 聚合或同一快照读取。

同一场地的并发读取合并执行，完成后共享最多 2 秒的结果；慢查询不会因执行超过 2 秒就重新发起。收到变更通知即清除读取缓存；被清除的在途查询可以结束自己的响应，但不能回写共享增量历史。总览的共享缓存按授权范围、角色、场地及筛选条件隔离。每种读取缓存最多 32 项；场地增量历史最多 32 轮、10000 条变更，超出后回到全量读取，不无限积累。

库位增量减少的是传输量；缓存未命中时，后端仍读取该场地全部库位来生成快照和差异，并非数据库也只查变更行。缓存按后端进程共享，多实例会各自执行一次读取。

旧 slots/stats 接口保留兼容已有调用。设置页、入库页、库位选择器原有的按需读取不等同于持续轮询。本次没有新增界面说明、提示区、功能按钮或业务操作。

## 验证范围

- React + DOM 自动化验证：已挂载的工作台页面隐藏后停止连接和请求，浏览器后台页不请求，返回页面重新同步，旧场地的迟到响应不能覆盖新场地，通知和重连能触发读取。
- 调度测试：100 个连续通知合并为一次读取，慢请求不重叠，隐藏时中止请求，失败后可以恢复。
- 真实 PostgreSQL + WebSocket：提交后通知、回滚无通知、多个后端监听、区域和策略变化、跨机构订阅拒绝、数据库监听断线恢复。
- 真实数据库验证 100 个并发看板读取只执行一次库位读取，并在缓存命中前重新校验场地权限。
- 模拟 10000 个库位、一个库位变化时，增量响应小于对应全量响应的 1%；这验证传输逻辑，不代表生产压测结论。
- 库存业务、迁移、组织隔离、前端权限回归以及前后端构建一起检查。

仍需观察生产实际并发、带宽、慢查询及首次大场地载入耗时。这次削减的是无效轮询、重复计算和全量传输，不对未经压测的承载上限作保证。总览仍返回整体聚合结果；库位增量协议仅用于场地看板。

## 2026-09-22 再次核验

结论是“场地库存操作提交后驱动两个看板刷新”，不是“全系统所有页面都订阅所有更新”。

| 实际入口或变化 | 提交通知来源 | 接收范围 |
| --- | --- | --- |
| 网页手工占位、网页/App 入库扫描、非计划入库 | 库位历史、车辆历史、库存流水，与业务同一事务 | 场地看板、运营看板 |
| 单车移位、批量移位、误入库撤销、盘点调整 | 同上；批量移位按每条成功事务通知 | 场地看板、运营看板 |
| 网页/App 装车、卸车、启运离场 | `InventoryService` 同事务写库存流水 | 场地看板、运营看板 |
| 库位冻结、区域容量/用途/启停、生成库位、场地启停 | 库位/场地历史和区域表触发器 | 场地看板、运营看板 |
| 订单、订单车辆状态、经营策略、日快照完成 | 订单、车辆历史、策略、快照运行表触发器 | 对应运营看板；策略也更新场地看板 |
| 库龄增长、超时预警、跨业务日 | 没有业务提交可通知 | 可见页面约 5 分钟校准 |
| 设置列表、入库表单的库位选择、其他业务列表、App 页面自身 | 保留现有进入页面/操作后读取 | 没有接入这套持续订阅 |

Android 已核对 `InboundRepository` 的 `/inbound/scan`，以及 `WaybillRepository` 的装车 `/waybills/:id/vins/:vin/load`、启运 `/waybills/:id/depart`。App 操作能触发网页看板更新，不代表 App 自身已订阅 WebSocket。

本轮补齐：

1. 机构用户在运营看板选中单场地时，同机构其他场地变化也通知该看板，因为重复 VIN 检查会比较其他可见场地。普通场地看板仍只订阅自己的场地；场地员工保持自己的场地范围。
2. 无效的迟到查询不能覆盖共享增量历史，包括缓存失效和监听重连清空历史两种情况。
3. 查询未完成时持续合并同键请求，完成后才计算缓存有效期。
4. 场地启停状态也纳入 board 的可重复读快照，防止取数过程中启停变更导致容量与库位状态不一致。

订阅的机构范围在建连时确定。新增子机构、调整机构树或成员授权后，需要重新建连才更新订阅范围；低频 HTTP 校准仍重新鉴权并读取当前范围。此类组织结构变更、场地选择下拉列表不属于本次全面实时化范围，不能承诺都在提交后立即更新。

本轮运行 77 项测试：后端单元 29、前端权限/刷新 20、真实数据库库存与通知 27、迁移 1，全部通过；后端构建通过。新增真实业务入口测试连续执行手工入库、单车/批量移位、装车、卸车、启运、扫描入库、撤销、盘盈、盘亏，并逐步核验提交后的通知与统计结果。测试连接关闭，隔离测试库在验证完成后删除。

## 数据库聚合与通知的可靠性边界

数据库聚合适合当前精确库存计数：使用现有库存事实和流水，不新增一套由通知异步维护的库存总数。相关索引支持按场地和在场状态筛选，但 `COUNT` 仍需读取符合条件的数据；缓存、通知合并和隐藏页停止请求才负责减少重复计算。

本地隔离库额外执行了实际 stats SQL 的 `EXPLAIN (ANALYZE, BUFFERS)`：新建一个 10000 空库位、0 在场库存的场地，单次预热后执行约 3.707 ms、规划约 0.330 ms，容量结果为 10000。该场地占测试库绝大部分库位，因此优化器选择顺序扫描，不能把“有索引”解释为“所有请求必走索引”。测试在事务中回滚。这不是多用户、满库存或生产压力测试，也不代表生产承载上限。

`LISTEN/NOTIFY` 用于提醒页面重新读取，不提供断线期间事件持久保存、逐条确认或重放保证。正确性由已提交的库存表和流水保证；刷新完整性由重新连接、重新进入页面和低频校准恢复。若以后要求每条消息必须被下游处理，才需要事务内持久事件表、可靠投递、幂等消费和重试，不能直接把当前通知当成可靠业务消息队列。

## OpenAI 公开文档可确认的做法

- OpenAI Responses API 支持 SSE 持续输出新增内容；这是模型响应传输机制，不能据此断言其内部库存式业务数据库如何刷新。[Streaming 文档](https://developers.openai.com/api/docs/guides/streaming-responses)
- 后台响应完成后可以发送 `response.completed` webhook，接收方再按响应 ID 获取结果。失败投递会指数退避重试，最长 72 小时；消费者需要处理重复事件。这是持久业务事件投递需求的参考，保障强于本项目的临时页面失效信号。[Webhooks 文档](https://developers.openai.com/api/docs/guides/webhooks)
- 官方生产建议包括缓存经常访问的数据，并在新增信息时使缓存失效；这是给应用开发者的建议，不能作为 OpenAI 内部数据库拓扑或聚合方式的证据。[Production best practices](https://developers.openai.com/api/docs/guides/production-best-practices)

上述公开文档没有证明 ChatGPT 内部使用本项目的 PostgreSQL 通知、缓存周期或统计 SQL。可借鉴事件驱动、增量传输和按可靠性要求设计恢复机制，不能声称本项目照搬了 OpenAI 内部实现。
