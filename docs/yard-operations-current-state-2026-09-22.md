# 场地运营与库内管理现状梳理

整理日期：2026-09-22。代码基线：`9460a2b`（新增权限管理）。

> 本文保留修复前的调查结果，以下“当前”和代码行号均针对该基线。后续修复、现行接口、数据口径及验证结果见 [场地库存修复与上线说明](yard-inventory-ledger.md)。

## 1. 结论及核实边界

当前项目已具备汽车物流的入库、库存定位、场内移位、出库开单、装车、启运、签收及追溯能力。场地管理的主体是“VIN 对应一个库位”，已有总览、预警和历史快照。

但从当前实现看，库内管理仍主要围绕位置和进出记录展开。盘点差异处理、车辆质量冻结、钥匙及随车资料交接、在库养护、异常责任及关闭、现场班组管理，尚未看到独立而完整的业务流程。部分日常操作还会造成库存关联、库龄、出库数量口径不一致。

这份报告分为三种判断：

- **已确认**：在当前源代码、页面或项目文档中找到直接依据。
- **风险推断**：代码存在相应路径，说明可能出现该结果；没有据此断言生产已经发生。
- **待现场确认**：未取得现场人员答复、实际业务数据或作业凭证，不能把“系统未覆盖”等同于“现场没做”。

本次核查了后端、网页端、Android 相关入口和项目业务文档。未连接生产数据库、未操作生产系统、未进行现场访谈；未做完整运行或并发测试。当前库存、真实利用率、作业效率、损失金额和系统实际使用率均待核实。只新增本文档，未修改业务代码。

## 2. 现有业务链路

### 2.1 经场地的车辆

客户入库计划导入 → 可选的供应商提货 → 到场扫码、照片、可选车检 → 手选或自动分配库位 → 在库查询/场内移位 → 客户出库计划 → 选择 VIN、承运商、司机及拖车 → 逐台装车并拍照 → 整单启运释放库位 → 逐台签收。

补充分支：第三方直送可以不经过本系统提货；计划外到车可以登记客户、场地、VIN，挂到散车订单后入库；已有批量库位分配入口，用于初始化和批量移位。

### 2.2 不经场地的车辆

纯 A→B 运输有独立的需求单、调度、趟次、异常、POD、报价及费用流程。不能把这些功能直接视为场地库内管理已覆盖，也不应将纯运输车辆计入场地库存。

### 2.3 当前需要区分的几个概念

| 概念 | 当前含义 | 管理时要注意 |
| --- | --- | --- |
| 已到仓 | 入库车辆记录为 ARRIVED | 出库后不一定改回其他到仓状态，不能单凭此字段当作当前在库 |
| 在场库存 | 占用库位上的唯一 VIN | 无库位的实际车辆可能不在该口径中；账实仍需盘点 |
| 已装车 | 运单 VIN 有装车时间及照片 | 当前仍保留原库位，直到整单启运才释放 |
| 锁定 | 库位有锁定字段，运单也有自己的锁定字段 | 两者含义不同；尚不能代替 VIN 质量冻结与放行审批 |
| 长龄 | 主要根据库位分配时间计算 | 不同操作会否重置时间，影响库龄可信度 |
| 今日进出 | 按日志事件统计 | 不是已经完成账实核对的净库存变动 |

## 4. 已定位的管理风险

以下优先级是本次梳理建议：P0 表示优先核实并控制库存、放行或数据范围风险；P1 表示影响指标、追溯及日常管理。均不表示已确认发生生产事故。

### R1｜P0：手工“占位”没有同步完成车辆入库

**已确认**：`assignSlot` 只改库位状态、VIN 和分配时间，没有同步 `OrderVin` 的库位和到仓记录，也没有在该方法中校验 VIN 属于哪张业务订单。网页场地看板有对应入口。

**影响推断**：可能出现“库位有车，车辆业务记录无位置”；库存总览能看到，而开单因缺少有效入库关联而失败。已有看板预警能发现部分关联异常，但不能代替入口一致性控制。

**需定规则**：手工占位是期初初始化、纠错还是正常入库；每种用途都应保证 VIN 与库位双向一致。

证据：`backend/src/modules/yards/yards.service.ts:170`。

### R2｜P0：“释放库位”实际是撤销入库

**已确认**：释放会在匹配的车辆记录上撤回到“预计到仓”，清空到仓时间、人员、库位、照片引用、车检、备注及批次。原入库审计附件可能仍保留，不能称为所有证据被删除。该方法未见已开单/已装车阻断和必填撤销原因。

**影响推断**：若操作员仅想清理位置、临时移出或纠正库位，可能误把真实入库事实撤销，并与已分配的出库业务冲突。

**需定规则**：分开“移位”“撤销误入库”“已发运离场”和“盘点调整”；撤销应留原因及前后记录。

证据：`backend/src/modules/yards/yards.service.ts:213`。

### R3｜P0：批量分配兼有初始化、入库、移位效果，保护规则不足

**已确认**：批量按 VIN 查询车辆，按目标场地检查权限；未见逐车核验其所属订单机构/源场地。预计到仓的车辆会被直接改为已到仓，并记作入库事件；该入口不要求标准入库照片。逐行提交，允许部分成功；重复 VIN 保留最后一行。

**影响推断**：初始化可能被当作日常扫码入库；部分成功可能导致现场误以为整批完成；跨机构/源场地修改风险需要重点测试。当前方法没有与普通移位一致的跨场地阻断，也没有显式使用同等级的行锁保护。

**需定规则**：初始化独立标记及权限、逐车归属核验、失败行复核、禁止借批量移位绕过调拨；并发结果需在测试环境验证。

证据：`backend/src/modules/yards/yards.service.ts:591`。

### R4｜P0：新旧启运入口规则不一致，签收仍可跳过启运

**已确认**：新 `departWaybill` 要求全部 VIN 已装车，且司机、拖车已分配。旧 `scan(DELIVERY_DEPARTURE)` 要求 SJ 附件，但没有相同的逐台装车校验，扫一个 VIN 可释放整张运单的库位。`SIGNED` 分支没有要求先处于运输中，并会兜底释放仍挂着的库位。

**影响推断**：不同入口可能产生不同放行标准；库存会减少，但逐台装车、启运或责任交接记录不完整。当前网页主流程使用新启运入口，旧接口存在不等于现场仍在使用，需核实调用情况。

**需定规则**：唯一正式装车/启运标准；漏扫补录须单独标识、留真实发生时间和处理原因。

证据：`backend/src/modules/waybills/waybills.service.ts:373`、`:735`；`backend/src/modules/waybills/waybills.controller.ts:136`。

### R5｜P1：批量移位会重置库龄，页面长龄阈值不统一

**已确认**：普通移位保留 `assignedAt`，批量分配写入当前时间；VIN 库存的库龄筛选/排序及看板长龄判断依赖该时间。运营场地网格固定 7 天，总览看板使用机构策略。

**影响推断**：一辆在场 20 天的车批量移位后，可能按刚分配库位计算库龄；机构长龄阈值改成其他天数时，两处页面颜色/预警不一致。

**需定规则**：车辆本次入场时间与库位移动时间分开保存；初始化实际到场时间不能默认为操作当天；统一阈值来源。

证据：`backend/src/modules/yards/yards.service.ts:318`、`:347`、`:703`；`frontend/src/app/(dashboard)/yards/YardBoardInner.tsx:41`。

### R6｜P1：“今日出库”和库存变化不能直接对账

**已确认**：今日出库按 `DELIVERY_DEPARTURE` 日志条数计；新启运逐 VIN 写日志，旧启运整单只写此次扫描 VIN 的一条日志；签收兜底释放库位不写启运事件。调拨启运也不在此出库指标条件里。入库撤销事件不从该日入库事件数扣回。

**影响推断**：同样一车拖走 6 台，新旧路径可能分别计 6 和 1；“昨日库存＋今日入库－今日出库”不一定等于当前库存。不能直接据此考核产能或判定丢车。

**需定规则**：分别定义实物入场、派送出场、调拨出场、退回、纠错、补录及期初导入；同时展示吞吐量与净变动。

证据：`backend/src/modules/dashboard/dashboard.service.ts:379`；`backend/src/modules/waybills/waybills.service.ts:536`、`:798`。

### R7｜P1：空位不等于可用容量，装车后的物理位置未独立表达

**已确认**：场地统计的空位为总数减占用数；总览总库位包含查询到的全部库位，没有在分母中扣除停用区域和锁定空位。自动入库分配却排除停用区域和锁定位。装车后原库位一直占用到启运。

**影响推断**：看板显示有空位，实际可能分配不了；车已上拖车时原库位仍显示占用，账面库位与物理位置阶段性不符。

**需定规则**：区分设计容量、启用容量、可分配空位、冻结/停用容量，以及停车位、待装区、已装待出场车辆。

证据：`backend/src/modules/yards/yards.service.ts:159`；`backend/src/modules/dashboard/dashboard.service.ts:121`；`backend/src/modules/inbound/inbound.service.ts:490`；`backend/src/modules/waybills/waybills.service.ts:650`。

### R8｜P1：有历史和预警，但不能保证每次业务成功都有完整审计

**已确认**：入库、移位等业务事务完成后再写审计；通用审计失败只写服务日志，不阻断已成功业务。日入库指标依赖这些审计事件。已有每日快照及数据库保护，但快照无法替代缺失的业务责任证据。

**影响推断**：故障时可能“库存已变，业务日志缺失”，进而影响时间线和事件型指标。

**需定规则**：关键业务事实与事件可靠落地，失败可补偿；先验证故障恢复，不宜宣称所有历史绝对完整。

证据：`backend/src/modules/tracking/audit.service.ts:19`；`backend/src/modules/inbound/inbound.service.ts:674`。

| 调拨/退回/重入库 | 跨场责任如何交接；途中归谁；拒收退回是否重检；同一 VIN 多次进场如何区分 | 调拨单、退回单及一台车完整历史 | 调度、收发场地 |
| 班组与交班 | 有哪些岗位/班次；谁接未完成任务；照片补传、未归还钥匙、异常车辆怎样交接 | 排班、交班表、岗位职责 | 场地经理、班组长 |
| 客户承诺与经营 | 仓储免费期、计费起止、额外服务、责任约定；按场地/客户核算哪些收入成本 | 业务条款、费率表、实际账单和成本明细 | 商务、财务 |
| 系统使用与连续性 | 是否存在事后集中补录、共用账号、Excel重复账；断网如何作业、恢复后谁对账 | 使用访谈、异常记录、备份恢复演练结果 | 一线操作员、系统负责人 |

养护、安全及责任事项应按已有客户要求和现场制度核实；本报告未制定统一养护周期、安全参数或法律结论。

## 6. 经营与管理指标：先统一口径，再设目标

| 指标 | 建议口径或拆分 | 当前能否直接可靠取得 |
| --- | --- | --- |
| 当前在场车辆 | 按本次入场记录识别未实际离场车辆；另对比库位占用 | 当前有占位 VIN 数，需先验证账实及异常入口 |
| 有效库位利用率 | 占用的可用停车位 ÷ 启用可用停车位；停用/冻结单列 | 当前总库位口径需要补充 |
| 库龄分布 | 本次实际入场至现在；移位不重置；按客户/车型/原因分组 | 有库龄查询，但需先统一起算点 |
| 账实及库位准确率 | 盘点范围内实物与账面一致数 ÷ 应核查数；漏扫不能当一致 | 需要真实盘点任务与结果 |
| 到场至验收/入位耗时 | 分开记录到门、卸车、验车、入位时间 | 当前单个到仓时间不足以拆分瓶颈 |
| 移车效率与重复搬运 | 移位任务耗时、无效移位次数、每台车累计搬运次数 | 有部分移位日志，缺完整任务过程 |
| 按时出库率 | 约定截止时间内实际放行 VIN 数 ÷ 当期应放行 VIN 数 | 需核实承诺时间、补录和异常剔除规则 |
| 异常处理 | 新增、未结、超期、平均处理时间；按责任及原因分组 | 场地异常工单闭环待补 |
| 质量及损失 | 入场已有损伤和保管期间新增损伤分开；按车辆/事件去重 | 目前照片和备注不足以稳定统计 |

在没有基线数据前，不建议把库位利用率、单人日产量或养护周期写成统一固定目标。

## 7. 下一步工作的顺序与完成标准

### 第一优先：确认库存和放行可信

1. 现场抽取正常入库、散车入库、手工占位、批量移位、撤销入库、装车未出闸、漏扫启运后签收的车辆，核对实车、库位、订单、运单和日志。
2. 核实手工占位、释放、批量分配、旧启运接口的实际使用人和使用频率，明确用途及权限。
3. 核对同一业务日的实物进出与系统事件，列明调拨、退回、撤销、初始化、补录形成的差额。
4. 确认库存归属、VIN冻结与放行规则，再形成修复清单；对跨机构和并发路径做专项验证。

**完成标准**：样本的实物位置、业务状态和账面关联可以互相解释；每笔差异有原因、负责人和处理记录；任何放行都能找到授权及实际执行证据。

### 第二优先：补齐日常责任闭环

建立盘点差异、车损、钥匙、养护、交班和场地预警的统一台账要求。允许先沿用现场已有工具，但要明确谁发起、谁执行、谁复核、何时完成、凭什么关闭，再决定系统化范围。

**完成标准**：上述事项不存在只有提示、照片或口头说明却没有责任人和关闭凭证的状态。

### 第三优先：再优化排程、指标和成本

在可信库存和标准作业基础上，优化有效容量、到发计划、人员安排、场内路线、库龄分层、客户服务及场地损益。

**完成标准**：每项指标有定义、数据来源、统计时点、负责人和异常处理方式；不同页面与不同业务入口结果一致。
