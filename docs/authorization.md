# 机构、角色与功能授权

采用组织范围内的 RBAC，不引入角色继承、逐人覆盖、通配符或策略表达式。依据 [NIST RBAC](https://csrc.nist.gov/projects/role-based-access-control/faqs) 的用户—角色—权限关系，以及 [OWASP 授权原则](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 的默认拒绝、逐请求检查。

## 三个独立概念

- **账号**：登录身份和全局启停。
- **机构成员关系**：当前机构、数据范围类型、可选场地绑定、成员启停。数据库中的 `role` 枚举只表示总部/机构/场地范围，不再等于岗位或全部管理员权限。
- **业务角色**：`access_roles` 中由管理员创建的角色，属于一个机构和一种数据范围，保存菜单与操作许可。`membership_access_roles` 支持一个成员分配多个角色。

一个会话只能选择一个机构。有效权限 = 当前机构成员关系中有效角色的权限并集，再受该数据范围的上限约束。其他机构的角色不参与合并。成员上的旧 `permissions` 字段已删除，不做运行时兼容或双轨授权。

每次请求从数据库校验账号、机构、成员和角色。JWT 不携带可信功能授权；改角色/撤权后原令牌下一次请求就受新权限约束。前端在页面启动、切换机构、重新聚焦及业务接口返回 403 时校验会话并刷新菜单；后端即时限制不依赖前端刷新。

页面启动时不直接信任浏览器持久化的权限，必须先通过 `/auth/me`；验证失败停止展示业务页面，清空菜单和已打开标签，可重试或重新登录。成员关系或机构已停用时，当前令牌不能用于切换机构，需重新登录选择仍有效的机构。

切换机构采用后端换发当前机构令牌、前端替换授权并整页重载。切换中禁止重复提交；旧令牌发出的迟到响应/401 不得写入新页面或登出新会话。持久化标签按用户、机构、场地绑定分区；无总览授权时不固定保留总览标签。客户地址数据只保留在当前页面，不跨会话全局缓存。浏览器标签页共享同一登录存储，检测到其他标签页切换或退出时重新加载会话，不支持同一浏览器存储下各标签页独立固定机构。

这里没有引入全账号单会话/令牌撤销表：切换不使以前签发的其他机构令牌自动过期；它们始终受各自令牌绑定的机构及数据库中现行成员授权约束，不会获得新机构权限。停用成员、角色或账号仍在后续请求即时生效。

## 数据范围与授权管理

- 总部：可在所辖机构范围内查询业务；按权限进行机构、用户、角色、系统发布和快照治理；不能导入、开单、扫码、调度、财务记账或维护业务主数据。
- 机构：只访问当前机构，不继承子机构的数据。场地范围在此基础上进一步限制到成员绑定的有效场地。
- 外部承运商/客户账号：继续按合作方绑定隔离，暂时使用固定的外部功能模板，不混入内部机构的可配置角色。
- 查看用户/角色菜单只赋予查询权；账号维护、用户机构/角色分配、角色维护分别授权。
- 非总部只能维护/分配不超出自身权限的角色，也不能撤销更高权限成员的授权。总部可以给业务机构分配业务权限，但不能因此在总部会话中执行业务。
- 不能修改自己的成员授权，也不能修改分配给自己的角色的权限/启停。角色已被成员引用时不能停用，须先调整成员角色。未分配角色的成员不获得功能访问权。
- 跨机构共用账号的全局资料及启停由总部维护；本机构管理者只能管理本机构成员关系，避免影响其他机构。

上述治理接口同样经过后端权限检查，前端隐藏按钮不是安全边界。角色变化记录结构化服务日志；当前没有单独的长期审计查询页面。

## 使用方式

1. 系统管理 → **角色管理**，明确选择维护机构。左侧搜索、选择或新建岗位角色，右侧编辑基本信息和权限；业务机构只能看到自己，HQ 可维护所辖机构。
2. 右侧按业务模块分组，再按菜单勾选“访问菜单/查询”及该菜单下的操作。勾选动作自动包含所需查询依赖，但不会开放其他菜单或额外写操作。显式保存；切换角色/维护机构或重新加载前，未保存的修改须确认放弃。本人已分配角色的权限、被成员引用角色的停用操作不开放编辑。
3. 系统管理 → **用户管理**，新建用户或编辑机构成员关系，选择同机构、同范围的一到多个角色；场地范围另选本机构场地。
4. 用户切换机构后只使用对应成员关系的角色。已分配角色的修改对引用它的成员共同生效。

没有用户角色分配权限的账号维护人员只能创建未授权账号，不能通过创建账号绕过授权管理。其场地选择使用受治理权限保护的最小目录接口，只返回场地 ID、名称和编码。

## 单一目录与新增功能

`backend/src/common/rbac/permission-catalog.ts` 是统一目录：菜单路径、分组、范围上限、查询依赖和操作集合都在这里定义。角色编辑器通过 `/roles/catalog` 读取它；导航通过登录及 `/auth/me` 获取同一目录，不再维护按固定角色复制的多份菜单。

新业务仍需要开发业务代码，但不需要开发新的授权机制：

1. 在 Permission 枚举登记功能码，在目录中声明可用范围、所需查询依赖及所属菜单；补显示文案。已有角色不会自动得到新增菜单/操作。
2. HTTP 入口声明 `@Permissions(...)`；多个码表示任一满足。未声明的业务接口默认拒绝。只有确实公开/仅会话认证的接口才使用对应的显式声明。
3. Service 复用 `ScopeService`，列表、详情、VIN、附件都校验归属；业务写入使用 `assertOrgWritable`，同时验证所有关联对象同机构。场地资源必须继续带场地范围条件。
4. 页面按钮使用现有 `usePermission`，无须新增角色枚举或写角色名白名单。新菜单自动出现在角色授权页面和导航目录。
5. 加入同机构允许、跨机构拒绝、HQ 写拒绝、查询与写入分离、撤权即时生效的回归。

查询依赖可以跨菜单，例如开单需要查询供应商，但这不会让供应商菜单可见，也不会授予供应商维护权。运输财务使用独立查询权限，运输业务查询不能读取报价/费用。不要把写操作藏进菜单的查询依赖。

## 迁移及验证边界

`1790200000000-ConfigurableAccessRoles` 将已有成员授权一次性转换为机构角色，随后删除旧字段；它不是兼容层。初始角色可以重命名，也可以创建更明确的业务岗位并重新分配。迁移目录被冻结，不引用运行时代码。

`organizations.e2e-spec.ts` 使用独立 PostgreSQL 和真实 HTTP，覆盖机构初始化、角色增改/分配、跨机构及场地隔离、权限并集、只读管理者、越权拒绝、旧令牌撤权，以及真实 `switch-org` 的 A→B→A、HQ→业务机构→HQ、撤销后的重登录和运行时无效角色过滤。授权单测检查全部 HTTP 入口显式声明权限和目录完整性。

在 backend 运行 `npm run test:frontend-auth -- --runInBand`，复用现有 Jest 工具链验证前端授权替换、预授权清空、上下文标签隔离、菜单路径校验及旧会话迟到响应。无须引入第二套测试依赖。

这些测试不代表所有业务异常分支、移动端菜单都已完整覆盖。Android 业务请求受同一后端权限约束，但移动端的菜单定制仍需独立验收。不要因为后端正确拒绝请求就认定每一个客户端交互已验证。
