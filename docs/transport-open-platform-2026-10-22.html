运输业务与开放平台

先统一运输事实、单号关系和交付机制，再用客户适配器承接不同接口。现有纯运输与库存作业继续负责各自的业务规则。

建议第一步：以 OTWB 状态回传为首个接入，完成“真实业务节点 → 标准事件 → 客户报文 → 回执与补偿”的闭环；随后开放标准下单和查询接口。

依据：本地代码版本 111b44a、项目业务文档、客户 Excel《08.10 运输状态回传.xlsx》。这是设计评估，未访问生产数据库、未调用客户接口，运行环境和生产迁移状态尚未验证。下文明确区分“当前实现”“建议设计”和“客户待确认”。

01 / 真正需要解决的事

业务目标

客户能提交运输委托、查到每台车的真实进度、收到可追溯的交付凭证。第二个客户接入时，复用同一套业务能力，只新增客户编码、协议和必要的差异映射。

成功标准

重复调用不重复建单；状态回传可重试、可对账；客户故障不拖慢场地作业；不同客户的数据隔离；接入新客户通常不修改提货、库存和签收核心规则。

约束来自现有业务：按 VIN 作业、允许拆单拼车、部分纯运输需求没有 VIN、库存存在独立在场周期、运输跨机构和客户、客户 API 状态含义各不相同。不能只靠一张状态对照表解决这些问题。

02 / 当前系统的三段运输业务

A. 纯运输：外部地点到外部地点

  1. 客户需求transport_orders
  2. 单车与分配transport_lines
  3. 趟次与提货transport_trips
  4. 发车与签收逐台完成
  5. POD / 费用凭证与签收分开

一台商品车一行，VIN 可以先空着。一张需求单能拆到多趟，一趟能拼多个客户、多个起终点。分组确认时可以只定承运商，司机和拖车后补；没有司机和拖车不能提货。

发车允许部分装载：至少一台已提货，未装上的明细退回待派车；计划外 VIN 必须先处理。逐台签收后生成应收应付，拒收/退回可以内部关闭；“趟次完成”可能包含关闭车辆，并不保证全部成功交付。POD 按趟次内的起终点组合上传，签收与上传没有强制先后闭环。

UNALLOCATED → ALLOCATED → DISPATCHED → PICKED_UP → IN_TRANSIT → DELIVERED；旁支为 CANCELLED 和 CLOSED。

当前实现：[1]。在场库存车辆被禁止走纯运输，包含已经装车、尚未离场的车辆。

B. 库存前段：港口 / 工厂提货到场地

  1. 入库订单orders · TRANSFER
  2. 分派承运商可指定司机账号
  3. 逐台提货order_vins.pickup*
  4. 到场验收入库照片 / 车检 / 库位
  5. 在场库存yard_inventory

当前是“订单级提货任务 + VIN 提货记录”。有提货人、时间、地点、GPS 和照片，但没有与纯运输等价的提货趟次、实际装车批次、车辆指派及独立发车节点。pickupStatus=COMPLETED 表示提货任务消化完成，不能当成运输已送达。

允许其他物流商送车直入：没有本系统提货记录，也能按入库规则接收。inbound_batches 是到货分组，可跨订单，不天然等同于起点的实际装车批次。

必须补齐的事实：要回传这一段的 0–4 状态，需要显式提货批次、装车车辆、出发/到达与交接凭证；不能由订单号或司机当天的记录猜一个 dispatchNo。

当前实现：[2]。第三方直入只报告我们掌握的入库事实，不补造前段运输节点。

C. 库存后段：场地出库到经销商

  1. 出库指令orders · DELIVERY
  2. 开单派车waybills / waybill_vins
  3. 逐台装车仍计在库
  4. 整单启运实际扣减库存
  5. 逐台签收全部签收后锁单

出库导入绑定已有 VIN 的 outboundOrderId，保留原入库单关系。可提前关联预计到仓车辆；真正开单要求车辆已到仓且有库位。同一运单限制同始发仓、同经销商、同出库单，创建时确定承运商、司机和运输车辆。

发车必须整单装齐：装车释放停车位，但库存转为 LOADED，仍在场；启运才关闭库存周期并写出库流水。签收不再扣库存。waybills.ARRIVED 在当前派送路径中由“全部 VIN 签收”触发，不是独立的车辆到达定位事件。

当前没有统一的“多张旧运单共享一个实际装车批次”对象；旧运单签收附件保存在扫描日志中，没有与纯运输一致的独立 POD 生命周期。

当前实现：[3]、[4]。代码保留 REALLOCATION 等历史枚举，但不能据此认定跨场调拨运输已具备完整可执行闭环。

03 / 客户接口实际要求什么

方向是 ALMS / 3PL → OTWB-Global。附件是一份运输状态回传契约，不是完整开放平台接口集。未提供真实地址、HTTP 方法、鉴权签名、限流、幂等约定、重试规则或下单/库存接口。表头虽写支持“整车及备件货物明细”，实际字段和示例未见 VIN / 件号 / 数量明细结构。

结构为一个 dispatchNo 携带多个 shipmentList 项；同一车辆、同一装车批次的多个运单应共享装车单号。flag=0 写的是“全量覆盖”，这直接决定我们需要保存客户可见的完整快照。

客户来源：Sheet3!A1:H36、A40:F44、B47、G47，见 [5]。

联调前须由客户澄清的契约

  1. 寻址与鉴权：测试 / 生产 URL、方法、Content-Type、token / 签名、时间偏差、超时和限流。附件没有这些信息。
  2. 标识与拆分：ShipmentNo 表格大写而示例小写；G29 混用 ordersn、subordersn、deliveryNoteSn。SO 拆到多趟、多段时，客户按哪个组合键更新？缺子单维度时不能自行拼接订单号。
  3. 全量覆盖：覆盖整张 dispatch、列表内每个 shipment，还是全客户？未出现项是否删除？空串是否清空？首期按明确签字的覆盖范围实现。
  4. 取消粒度：flag=1 撤销 dispatch、某个 shipment 还是上次状态？部分车辆换车 / 退组后如何表达，是否能撤销后重建？
  5. 状态 3 / 4：G30 同时写“已交货 / 已到达”和“已收货 / 文档上传”。是否要求交付与 POD 都完成？拒收、退回、部分签收如何回传？
  6. 实际时间：状态 3 要求目的地 ATA 和 ATD，但只提供一个 actualTimeOfDeparture；和状态 2 的始发 ATD 是否冲突？多起点、多目的地时 ETD / ETA 及头部地址如何表示？
  7. 数据前提：只有日期时是否接受估算？预计时刻由谁提供、多久更新？address 50 字符限制；mapurl、POD 等 C 条件的准确规则。
  8. 回执与幂等：E42 示例为 success，F42 定义成功码为 000000。业务成功判定、整批原子性 / 逐项结果、重复请求、超时结果查询、旧版本拦截规则是什么？
  9. 文件：客户立即下载还是保存 URL 延后读取？可用公网域名、下载认证、最长 URL 200、有效期、格式、多个 POD 的表示方式。
  10. 范围：本次接入是否只做整车道路运输？如果还做备件、铁路或水运，需要额外业务模型和协议；附件的“支持”不能视为 ALMS 已支持。

04 / 对外统一什么

建议建立统一的对外资源模型，第一期以映射表和查询投影承接既有数据，不迁移两套运输表、不新建一套竞争性的内部状态机。缺失的提货批次和业务节点在所属模块补齐。

服务委托		客户买什么：纯运输、提货入库、出库派送；串联关系可选映射 transport_orders 或 orders。库存订单不强制和前后运输共用一张单

运输段 / 站点		有顺序的起终点、预计与实际到离时间DIRECT、INBOUND_PICKUP、OUTBOUND_DELIVERY；一个客户运输单可有多段

实际装车批次		一次真实车辆执行；关联被承运的 shipment / leg / items纯运输映射 trip；库存前段新增执行批次；库存后段补共享装车批次关联
InventoryStay
在场周期		每次入场至离场的事实，不是运输状态yard_inventory + inventory_movements，保留独立账本
Document / Event有授权范围的凭证；带发生时间和版本的事实统一 POD 关联；业务事件保留来源模块、原记录、车辆覆盖范围

关键关系：客户委托与实际装车是多对多关系。一个 SO 可以拆多趟，一趟可以承运多个 SO；一台车的前段提货与后段配送是不同 leg。VIN 不可作为唯一事件关联键，否则历史多次运输、返库再发运会混在一起。

一个具体例子

客户 A 的 SO-001 有 8 台车，分到 D1（6 台）和 D2（2 台）；D2 又装了客户 B 的 2 台。ALMS 对内保留这两个真实批次。给 A 的 D2 快照只含 A 的 2 台所属 shipment，给 B 的报文只含 B 的内容。若 OTWB 只能按 SO 单号覆盖、不能区分 D1 / D2，则必须先让客户确认子单或拆运聚合方案，不能先接上再修数据。

同一 VIN 先“港口 → 场地”，再“场地 → 门店”，分别拥有 legId；两段中间是 InventoryStay。后一段开始时不把前一段“已到达”倒退成“配车”。

运行上先复用 NestJS、PostgreSQL、Redis / BullMQ 和 MinIO。回传 worker 独立进程、独立并发预算，避免客户慢接口占用业务 API 资源。当前队列已有基础，但 notification processor 只是打印日志；Socket.IO 和数据库实时通知服务于界面刷新，不等于可靠外部交付。

机器身份与业务权限

建议标准入口使用独立应用身份，采用 OAuth 2.0 client credentials 交换短期 token；适用于机密客户端的机器间授权，见 RFC 6749 §4.4。OTWB 出站鉴权按客户实际协议实现，不能假设客户也用 OAuth。

应用绑定机构、客户、环境和 scopes（如 transport:write、shipment:read、inventory:read），服务端推导数据范围，不信任请求自报的 organizationId / customerId。内部服务需支持受限机器 actor；当前纯运输创建要求内部用户，不能简单给客户一个管理员 token。共享趟次的明细、POD、位置轨迹都要做客户切片。

标准 Webhook 使用时间戳、deliveryId 和签名，支持密钥轮换与防重放。出站域名按连接配置约束，防止配置把请求或文件下载引向内部地址；日志保留脱敏诊断内容，不回传内部成本、其他客户订单或不必要的司机资料。

标准事件示例：与客户字段解耦

事件封装可采用 CloudEvents 1.0.2 的 id / source / type / subject / time 结构；业务版本、客户范围和运输段放在自有 data 中。以下为建议示例，不是客户真实报文。

  "id": "evt-example-0001",

  "type": "alms.transport.departed.v1",
  "subject": "legs/leg-example-01",
  "time": "2026-10-22T03:00:00Z",
  "datacontenttype": "application/json",

    "organizationId": "org-example",

}

outbox 必须同时保存形成该业务事实所需的状态与关联快照，不能只留下 ID 再读取已经变化的业务表。适配投影确定处理到哪一个版本，交付报文记录该版本。发生时间、接收时间、发送时间分开；迟到事件保留事实，但不无条件回退当前状态。

06 / 状态回传必须可恢复

  1. 业务事务：更新提货 / 启运 / 签收及必要审计，并写 outbox。事务失败一起回滚，事务内不发 HTTP。
  2. 可靠转交：relay 领取已提交 outbox，使用短事务租约和可恢复游标；提交后进入队列。交付任务先持久落库，Redis 丢任务后能由未完成记录恢复。
  3. 客户投影：按 connection + customer + dispatch 汇总当前已处理版本的完整 shipmentList，保留仍属于该批次的其他单据。映射版本固定，必填缺失进入“待补数据”，不造占位时间或地址。
  4. 有序发送：相同客户 dispatch 串行；还要检查客户实际覆盖键。若客户按 shipmentNo 跨 dispatch 覆盖，同一 SO 也须协调或阻止不支持的拆分。不同客户连接并发隔离。
  5. 判定成功：HTTP 与业务 code 一起检查；成功码待客户确认。保存请求摘要、每次响应、耗时与错误分类。批量接口若没有逐项回执，不能推定部分成功。
  6. 失败处理：网络错误、超时、429、可重试服务错误按退避加抖动重试；参数错误等待修正，认证错误暂停该连接并告警；人工补发有操作审计。
  7. 对账：有客户查询接口时核对外部状态；否则采用双方日志 / 业务清单核对，只能确认收到的回执，不能声称外部最终状态完全一致。

特别处理“超时但客户已成功”。这是结果未知，不是确定失败。优先使用客户幂等键或查询确认；如果客户都不支持，至少保持同一版本报文重试、严格单流发送并隔离旧版本。单靠本地串行无法阻止客户异步处理旧请求覆盖新状态，此限制必须在联调中解决。

“全量覆盖”的快照是该连接授权范围内的完整快照，绝不是整个内部跨客户趟次。业务取消时产生新的取消事实和 tombstone；旧运单目前会硬删除，所以取消载荷必须在删除同一事务里固化。撤销重建和部分退组要保留旧、新 dispatch 的关系。

入站幂等也要做在事务里

标准建单接收 Idempotency-Key：同应用、同操作、同 key、同请求 hash 返回原结果；同 key 不同内容返回冲突。外部订单号另设唯一约束防换 key 重复。持久 inbox、业务写入、external_reference 和结果需要同事务，或用明确可恢复的受理 / 执行状态机；不能“先查有没有，再建单”。

现有业务 service 大多自己开启事务。实施时需抽出可复用命令并接受同一事务 manager，保留原有网页 / App 调用；权限 actor 明确区分人和应用。不能通过调用内部 HTTP 接口来假装具有跨表原子性。

POD 的交付

现有 /storage/preview 是相对路径，用户签名链接有效 15 分钟并依赖用户权限。它不适合直接写入客户长期保存的 docUploadURL。建议新增针对接入应用的 document grant，通过对外可达 HTTPS 地址交付；有效期覆盖客户下载和补偿窗口，可撤销并审计，URL 保持在客户 200 字符限制内。

如果客户保存永久链接，则提供受控稳定入口或双方确认的文件推送方案；如果客户即时下载，则按约定发足够时长的授权链接。共享趟次 POD 还需按客户 / shipment 确认内容范围，多文件不得静默只取第一张。

现有文件机制：[7]；硬删除与通知窗口：[3]。

接入前应处理的代码风险
  • 提货完成数重复扣减：remaining = total - pickedUp - arrived - cancelled 中，已提货与已到仓重叠。3 台车中 A 已提且已到仓、B 已提、C 未提，现公式得到 0，实际剩余 1。建议改为逐 VIN 互斥条件计数，并核对受影响订单。已用独立样例验证算式，未在业务库复现或修复。
  • 提货事务不统一：pickupOrderScan 分别保存 VIN、订单状态和 best-effort 审计；旧 pickupScan 又是另一入口。事件化前收口到同一业务命令、并发锁和事务，避免事实写成而事件丢失。
  • 通知不是交付：旧运单提交后才发队列通知，失败仅记录日志；队列处理器目前不调用客户。不能沿用这一点位并宣称绝不漏报。
  • 文件授权不能照搬：人员预览 token、内部相对链接、跨客户拼车的段级 POD 都需要面向客户应用重新约束。
  • 完成与历史时间：纯运输“完成”允许 CLOSED；部分代录使用当前服务器时间。对外必须保留真实结果和节点时间来源，不由最终状态倒推不存在的历史事实。

后来每家客户怎么接

  1. 选业务范围与能力清单，明确谁是订单 / 库存 / 运输状态的权威来源。
  2. 配置应用授权、连接和凭据；导入客户、承运商、地点、单号映射，未匹配数据进入待处理队列。
  3. 选择标准 API / Webhook，或增加一个协议 adapter。字段重命名、编码枚举和固定格式通过版本化配置表达；拆单语义、补偿规则用有测试的适配代码。
  4. 运行固定契约用例、故障重试和跨客户隔离验收，形成双方确认的 mappingVersion。
  5. 沙箱、影子报文、小批量启用，再扩大范围；运营在交付列表处理失败，按日核对漏单和状态差异。

平台能标准化的是重复的接入工作。客户新增真实业务能力或不兼容的状态语义，仍需要明确设计；首期不做任意脚本映射引擎，也不承诺所有客户零代码接入。

08 / 性能与验收同时设计

以下为建议的初始测试门槛，须根据真实日量、活跃车辆、客户限流和当前服务基线校准；不是已达到的指标，也不是客户 SLA。

方面设计要求验收场景 / 初始门槛
业务接口开销业务事务仅增加有界事件写入；按命令批量写，不逐 VIN 请求客户同负载、同数据集与基线比较：提货 / 启运 / 签收 p95 增幅 ≤10% 且增量 ≤20ms；业务事务内外部 HTTP 次数为 0
故障隔离worker 独立进程和连接池预算；每客户并发、速率和熔断独立客户持续超时 / 429 时，其他连接及业务 API 仍满足基线门槛；队列不无界占用内存
正常时延outbox 有索引短批扫描，避免全表轮询；指标含最老未交付年龄数据齐全、客户健康时，从业务提交到业务成功回执 p95 ≤60s
恢复与积压尝试租约可回收、未完成 delivery 可重新入队；客户允许范围内限速追赶模拟 worker / Redis 故障和客户停机 15 分钟；恢复后测试持续输入下 30 分钟内清理积压，需客户配额允许
重复 / 乱序版本、幂等、不可变报文、按覆盖键协调同事件重复 10 次、旧事件晚到、超时已成功、处理中宕机：无重复建单 / 扣库 / 费用，无确认后的状态倒退
查询成本客户隔离投影、游标分页、连接+外部ID唯一索引；避免每条 VIN 再查一遍全历史用目标峰值数据检查查询计划、慢 SQL、扫描行数及连接池；库存差异为 0
GPS 与文件GPS 批量入库，状态与定位分队列；按约定降采样；图片不嵌事件 payload，下载流式传输大量轨迹及 POD 下载不阻塞业务事件；过期文件可恢复授权，越权文件下载被拒绝
存储与审计事件 / 投递日志分冷热，成功记录按约定归档；失败和未完成记录不因 TTL 丢失测平均 payload、索引 / WAL 增量及保留期，演练归档后查询；监控待补数据、死信、认证失败和外部差异

为什么轨迹需要单独预算

仅作容量示例：每天 10,000 台商品车、每台 6 个业务事件，约 60,000 个事件 / 日（未考虑批量合并及重试）。若 500 辆拖车每天运行 12 小时、每 30 秒一个 GPS 点，则约 720,000 点 / 日；每 5 分钟对外一次仍有 72,000 次候选位置更新 / 日。业务事件、GPS 点和 HTTP 请求量不能视为同一个数。

存储预算用“事件量 × 实测平均报文大小 × 保留天数”，再加索引、WAL、重试记录和附件存储；压测按实测峰值至少 2 倍准备，同时服从客户配额。OTWB 当前附件未规定持续定位频率，不能自行按每个 GPS 点回传。

固定业务验收集
  1. 纯运输 6 台计划、仅装 4 台启运：2 台退组，回传快照与实际装载一致。
  2. 同一 SO 拆多趟、同一趟拼多 SO / 客户：单号唯一且无数据越权；不支持拆分的客户协议明确阻断。
  3. 库存前段多批提货、第三方直入：不提前完成，不补造取货或发车时间。
  4. 出库装车、卸车回库、启运、签收：库存增减依次 0、0、−1、0。
  5. 部分签收、拒收关闭、POD 先到 / 后到、重复上传：交付结果和凭证分别正确。
  6. 改派承运商、撤销运单、部分退组：历史快照存在，客户侧取消范围准确。
  7. ETD / ETA / 地址缺失、超长字段、编码未映射：进入待补数据，业务不被外部回传阻塞。
  8. 同幂等键不同 payload、跨客户对象 ID、无授权 POD、伪造 tenant：拒绝并留下可诊断记录。
  9. 服务提交前崩溃 / 提交后崩溃 / 入队后崩溃 / 外部已成功但响应丢失：逐个演练恢复边界。
  10. 已有历史业务：明确 cutover 时点，仅经确认补发历史；缺失的里程碑不按当前状态自动合成。
